# Product And Feature Map

GentlePath combines a private family workspace, shared community/editorial content, and staff operations. The table identifies the code owner; the sections below retain the rules that are easy to miss. Schemas and registered adapters are authoritative for exact fields and commands. Shared transport/auth rules live in [integrations](INTEGRATIONS.md), not separate per-feature copies.

## Permissions And Privacy

- Public users read landing/published articles. Account actions require authentication without blocking public article reading.
- Every signed-in role owns its own children, journals, documents, observations, preferences, devices, and saved pivots. Admin/SuperAdmin do not gain access to another family's private records.
- Staff author reviewed resources/guides/blogs, administer milestones/commercial content, and review public reports/tips. Author-only post/comment/poll/tip edits remain author-only for staff too.
- SuperAdmin additionally controls platform/account permissions. Delivery tools also require the live backend's external-ID allowlist; role alone is insufficient. Self/final-active-SuperAdmin safeguards apply.
- No AI inference, clinical assessment, family-sharing, payments, billing, or data-erasure workflow is implied by the existing screens.

## Family Records And Documents

Record cards open details/editors from their main surface and place permitted secondary actions in a top-right vertical ellipsis. Editable record dialogs include their permitted delete/remove action. Family cards occupy a full row per child and display the name, calendar age, date of birth, optional gender, and every completed support answer in a responsive summary grid. Profiles persist optional gender, support notes, allergies, communication, sensory needs, comfort strategies, and daily routines. The single-line name field precedes date of birth and the shared gender dropdown. Gender accepts Female, Male, Nonbinary, Another Gender, or Prefer Not To Say; leaving it unselected stores `null`. Support text fields start at one line and grow. Saved cards use direct filled-bookmark toggles; unsaving does not delete source content.

Private journal search/drafts and the child/personal filter stay out of URLs and browser storage. Reflections support multiple feelings; the picker shows selected labels separated by commas. Cards use a translucent feeling-gradient header and a full border, with every feeling, child/personal token, and date below the divider. New reflections start with Hopeful and the first available child selected; Personal Entry is explicit. Saved custom feeling labels remain available when editing. Child references must belong to the current account. Child removal follows the canonical API's soft-delete visibility: linked journals, documents, and observations become inaccessible; unlinked personal records remain available. Demo retains hidden linked records internally and enforces the same visibility.

Document facade `/portal/documents` maps to `/care-documents` in [the family API](../../GentlePath-API/docs/FAMILY_RECORDS_API.md). Models, service, and live adapter live in `modules/documents`; metadata editing changes title/type/owned child, not the uploaded file or owner.

Uploads accept PDF/JPEG/PNG/WebP up to 10 MiB, with server-side body/signature checks. Show Preview opens the authenticated `/portal/documents/{id}/preview` facade in a new tab. Its live adapter rechecks canonical metadata/download authorization, retrieves only the matching AWS S3 signed object server-side with bounded reads and cancellation, and serves validated bytes inline with sandbox, no-store, no-sniff, and single-range PDF responses. Private uploads never receive active same-origin script access, and previews expose neither storage URLs nor API credentials. Live downloads retain validated HTTPS signed attachment URLs without API credentials/referrer; issued URLs may remain valid until expiry. Demo previews/downloads serve validated stored bytes through the same private facade and current account/child visibility rules. Upload progress is indeterminate; cancellation can race a completed server write, so refresh/check before retrying. Demo upload idempotency is not a live guarantee. Metadata uses last-write-wins semantics; deletion does not promise permanent object erasure.

## Resources And Guided Steps

`EditorialService` and its server adapters map `/portal/editorial/*` and `/admin/editorial/*` to `/resources` and `/guided-steps`. [Reviewed content API](../../GentlePath-API/docs/REVIEWED_CONTENT_API.md) owns canonical types, formats, provenance, collections, and replacement semantics.

Guides retain item IDs and derive order from the complete array; a dedicated reorder includes every active item exactly once. Current step is local reading state, not completion/assessment. Each step supports its own optional image. Source metadata remains editable for editorial records, while family resource and guide readers omit attribution panels. Resource collection navigation and external content links remain available.

Noncollection resources require source name/URL. Publication dates cannot be future dates; review attribution comes from staff identity/server time and does not mean clinical review. Collections may omit sources; reject self/descendant cycles and retain collection type while children exist. Removing a collection hides descendants through ancestry visibility. Preserve unrelated metadata during replacement. No revision-precondition contract exists for these writes.

The live adapter also bridges the existing family `/portal/resources` library and resource-save facade. Keep canonical type/format separate from family category/read-time metadata. Follow all required pages with nonadvancing/upper-bound protection, never silent truncation. Resource aggregates flow through the same list mapping, so gold rating summaries on cards/header require no per-card queries.

## Ratings, Likes, And Saved Content

`/portal/engagement/*` maps to resource-rating, blog-like, and typed favorite endpoints in the reviewed-content API. Resource ratings are one integer 1–5 per account; changes replace that rating. Shared StarRating owns accessible radio interaction; RatingSummary owns compact aggregates. Clicking the current selected star opens a confirmation to clear that rating, with no destructive removal button. These APIs rate resources, including guide-format resources, not Guided Steps. Resource readers place artwork first and use a spacious header without breadcrumbs.

Favorites support visible public content kinds, excluding private journals/documents. Validate the target before paging/creation, including ancestor/author visibility, published blogs, and approved tips. Removing an existing pivot remains idempotent after its target disappears. Resource saves share the same authoritative backend pivot/demo resource set with legacy controls and overview counts.

Saved previews use safe typed summaries (bounded text) and known internal reader paths. Published article slugs enable direct reading; older summaries without a slug use Saved Preview. Public article controls use the focused optional-account container; editor previews do not mount engagement controls.

## Community Posts And Polls

Post facade `/portal/community/*` maps to `/posts`, `/post-comments`, post/comment likes, and `/reports`. See [posts](../../GentlePath-API/docs/COMMUNITY_POSTS_API.md) and [moderation](../../GentlePath-API/docs/CONTENT_MODERATION_API.md). Lists, scope, tags, and pages are URL state; validated list return paths preserve filters. Only authors edit/delete; deleted parents hide their discussion. Reports retain original evidence and owner-scoped history/review details after source changes/removal.

Posts use a single vertical feed with author/avatar headers, permission-aware action menus, and forum-style detail/reply surfaces. Hide Post is an account- and demo/live-scoped preference on this device, with Undo and Show Hidden recovery; it is not server moderation or cross-device hiding. Post detail preserves open forms during transient background errors and offers retry; 401/403/404 still remove inaccessible content. Shared ReactionButton owns red filled-heart state, Like/Liked copy, confirmed animation, accessible counts/pressed state, and reduced motion. Comment actions use a chat bubble.

Posts and polls accept up to ten ordered public attachments (`IMAGE`, `VIDEO`, or `LINK`) with descriptions. One shared editor/reader owns both flows; images show descriptive alt text, direct videos use native controls, and recognized YouTube/Vimeo videos reuse the opt-in blog player. Permanent public HTTPS rules reject credentials, query/fragment tokens, local/private hosts, and vault paths. Legacy post `image_url` remains readable; omitted attachment arrays preserve existing media for older replacement clients. Cards and readers keep a direct Save/Saved control at the right of the comment footer, in addition to their action menus.

Discussion lists request roots with `root_only=true` and independently page direct replies with `parent_comment_id`. Web models/facades map the immutable parent link as `parentCommentId`. New replies target only visible roots of the same post or poll; a reply cannot receive another reply. Authors can edit bodies or remove their own comments/replies, and hiding/removing an ancestor hides its descendants before counts, reactions, reports, or saved-target resolution. Query invalidation refreshes roots, replies, and parent counts after mutations. Reply/edit drafts stay mounted through recoverable read failures and failed writes; authoritative access failures still remove inaccessible discussion content. Demo fixtures include one-level replies and enforce the same ownership/depth/ancestor rules.

Current live viewer-like enrichment is bounded parallel per-row reads because the API has no batch viewer-state endpoint: feed 1 list + up to 9 like reads, detail 2 reads, root comments 1 list + up to 10 like reads; each reply page adds 1 list + up to 5 like reads. An arbitrary page of all account likes is not a correct substitute. Moderation cards open from their full surface: open reports enter review and resolved/dismissed reports expose read-only review details. Search/status combine with Latest Reports, Oldest Reports, Recently Reviewed, or Content Title A–Z sorting before local pagination; sort changes reset the page and retain URL/history state. Staff moderation currently exposes only the newest 100 reports and cannot hide targets; [integration limits](INTEGRATIONS.md#api-proxy-and-mapping) explain the bridge.

Poll facade `/portal/polls/*` maps to the [poll API](../../GentlePath-API/docs/POLLS_API.md). Options have stable IDs; ballots select distinct active options from that poll. Single choice means exactly one, multiple means one or more. Ballot reads are private; results expose aggregate participants/selections. Multiple-choice percentages may exceed 100% in total.

Any retained ballot, including one from an inactive account, freezes question/message/media/mode/option labels and membership. Tags and reordering unchanged choices remain editable; preserve drafts on conflicts. The API has no close/reopen/expiry lifecycle. Poll cards and forum-style details share all answer options, aggregate distribution bars, and selected-ballot state. Clicking an option fills its selection surface; Cast Vote commits the complete single- or multiple-choice ballot; an unchanged recorded ballot reads Vote Cast, and changed choices use Update Vote. The choice-mode token sits below the shared author/avatar/menu header. Poll discussion has author-only edits and shared heart reactions. Confirmed votes, comments, saves, and likes have shared particle feedback that respects reduced motion.

Content tag words are capitalized throughout web/API inputs, outputs, and filters; acronyms and existing mixed-case names are preserved. Duplicate case variants are rejected. Retained demo state upgrades without reset; existing database rows require the tag backfill migration.

## Milestones And Reviewed Tips

The family UI uses `MilestoneAdminService`, `/portal/milestone-tools`, `/portal/milestone-observations`, and `/portal/tips`; staff writes use their matching admin facades. [Milestone API](../../GentlePath-API/docs/MILESTONES_API.md) owns historical option and review rules.

Milestones preselects the first child in a token picker, shows individual floating milestone cards, and supports a progress multiselect. Its segmented overview shows answered/unanswered totals and each response category across the entire visible catalogue, using the selected child's latest observation per milestone. The owner-scoped `/portal/milestone-tools/progress` facade maps to `/milestones/progress`; its counts ignore directory filters and pagination, refresh after observation/guidance changes, and retain retired response classifications. Segments remain mounted at zero width and animate between response counts, including child changes; busy reads retain the prior summary until the next one arrives. The unanswered track uses a quiet theme gradient; labels and counts describe every segment without relying on color. Child/progress filtering uses the latest visible observation before pagination. Standard starter responses are Not Yet, Beginning To Notice, Happening Often, and Stopped; historical values stay stable. A card's status picker writes a current-timestamp observation without notes. The card opens a details modal for notes, edit/delete, history, approved tips, information, and bookmarks; these secondary actions are also in its ellipsis menu. The API includes a checked-in, categorized/tagged 18-entry starter catalogue; its dedicated `npm run seed:milestones` command loads only that catalogue without unrelated sample fixtures. Seed data does not imply clinical assessment or age-based comparison.

The admin milestone directory supports multi-tag selection through the shared MultiSelect. Selected tags match any tag on a milestone, combine with search before server pagination, and reset the offset when changed or cleared. Repeated `tags` URL parameters preserve individual names and browser history; legacy single `tag` links remain selected until the next tag edit converts them. The shared control caps selection at 30, keeps selected options removable, and offers Clear Tag Filters. Guidance reads retain prior results during filter refreshes; the directory's progress line announces pending work. Family milestone and tip screens keep their existing single-tag control.

Staff milestone editors support an optional header image through the shared public-image field: upload, replace, remove, or paste a permanent HTTPS URL. Cards render the image above their tags/title when present and retain a stable fallback if loading fails. `image_url` is nullable in the API; omitted replacement values preserve it and explicit null clears it. Apply the API's additive milestone-image migration before serving the updated live API. Guide covers and each ordered guide step use the same upload field and preserve image association when reordered. Public uploads go through the container-owned image service and staff-only `/admin/media/images` facade to the existing backend `/media/upload-media`; PNG/JPEG/WebP/GIF are limited to 5 MB and uploads block save/navigation until settled. Removing an image clears the content reference; storage retention remains backend-owned.

Response IDs/values stay stable. Save the active options in full order; retiring an option preserves history, reserves its value, and does not restore it later. Referenced labels cannot change; the server can reject a change even when the UI cannot know references exist. Observation edits retain child/milestone identity and may keep an unchanged retired choice when correcting date/notes. New selections use active options belonging to that milestone. Dates are past/current instants; history stays private to the owned child.

New/edited tips become Pending; author edits clear prior review details. Rejection needs a note; reviewer/time are server-owned. Staff review never grants author-edit rights. The API exposes the current decision, not a chronological review audit. Hidden milestones/removed children/accounts are excluded from private overview counts. Dynamic demo state, rather than the old fixed-response array, is authoritative.

## Commercial And Family Discounts

Family Discounts supports Latest First, Oldest First, Ending Soon, and Title A–Z sorting in URL state, resetting pagination on sort changes. The web facade sorts the complete eligible catalogue before pagination; alternate live orders read all upstream pages with cancellation and bounded/nonadvancing-page protection because the API has a fixed newest-first order.

Staff can create/manage offers directly from Family Discounts or `/admin/commercial/offers/new`. Select an eligible approved sponsor, save content, approve review, verify against a source with valid dates, then enable the offer. A new/editable record is not automatically eligible for family serving.

`CommercialService` maps reader `/portal/commercial/*` and staff `/admin/commercial/*` to sponsors, discount offers, campaigns, creatives, placements, and aggregate metrics. [Commercial API](../../GentlePath-API/docs/COMMERCIAL_API.md) defines the commands.

Content edits reset review and serving enablement; offer edits clear verification. Sponsors have review/suspension rather than an enable flag. Immutable attribution/relationship fields require new records to change. Offer verification must remain valid and within expiry; affiliate content needs its disclosure. Placement replacement preserves association identity/history, complete order, and retired metrics. The two reserved placement keys remain reserved after deletion.

Serving checks eligible parents/offers, dates, review, enablement, verification, locale/platform, and disclosure before limiting results. Carousels respect pause, hover/focus/background/reduced motion. Authored colors stay within creative artwork; disclosure/action regions retain the readable theme. Approved app destinations resolve known web routes; blog UUIDs resolve published slugs. Framed partner pages retain an external-link fallback.

Metrics are daily submitted aggregate impressions/clicks/code copies, not unique people. No private family/device/health data becomes targeting. Browsing and staff preview do not automatically ingest metrics or call Amplitude; explicit demo impression simulation only changes local state.

## Notifications

`NotificationInboxService` maps `/portal/notification-inbox/*` to `/notifications` and `/user-settings`. Only the account's published, in-app-enabled, non-archived/non-expired records are visible. Opening/following an update never implicitly marks read. All/Unread/Read, search, category, order, and page state remain explicit and shareable.

Counts ignore the selected read-status filter; the shell bell counts the entire account. Bulk actions state whether they affect all or filtered records across pages. Archive has no promised restore/Undo and uses destructive confirmation/styling. Only supported same-origin destinations become actions. Record-specific updates carry the target detail URL, rather than a directory URL. Journal links use `/journal?focus=<entry-id>`: the owned collection selects the containing page, scrolls to and focuses the matching card, and reports unavailable/foreign IDs without opening another reflection. Existing `/journal?entry=<id>` editor links remain separate. General workspace updates can still open the dashboard.

Category/channel preferences apply to future notifications and are separate from FCM/browser authorization. Effective scheduling timezone is explicit override → last detected browser zone → UTC. Nonblocking detection records only the last zone and cannot replace an override. Displayed dates still use browser timezone. The inbox and Appearance share browser push controls. An unanswered browser choice adds one setup alert to the header bell independently of unread counts. Choosing enabled or off removes that setup alert; off/blocked browsers show an inline warning while keeping the inbox readable. Demo choices are simulated without browser permission requests or Messaging initialization.

## Account And Operational Tools

Admin summary cards link to their corresponding people, active-account, published-story, and open-report directories. The complete illustrated hero opens story authoring. People filters expose the three current platform roles and a separate URL-backed account-access filter; legacy roles remain readable only for historical live records. My Path summary cards link to the owning private family sections.

The sidebar account footer opens `/profile`, which combines the profile form, device management entry point, operator tools when authorized, and account deletion. `/settings/account` renders the same combined screen for existing links. Saved Content is reached from the My Path dashboard, rather than the sidebar. Staff navigation places My Path immediately after Administration; opening it from the admin experience first checks dirty forms, then confirms leaving administration. Notifications are reached through the header; Account And Devices, Notifications, Developer Settings, and Stories And Insights are absent from sidebar navigation. Developer and public blog routes remain available directly.

Appearance offers two side-by-side Light/Dark choices and browser notification controls. Accent and motion selectors and the analytics settings section are not shown. Device reduced-motion preferences and the existing consent-gated analytics service remain in effect.

`AccountToolsService` maps account/devices/Help to existing users/devices/system endpoints; operator delivery/attempt tools map to their dedicated APIs. Pass trusted current identity and role through the proxy. Never return device tokens, provider identifiers, delivery destinations, or leases to the browser.

Account deletion verifies typed current email plus acknowledgement. It soft-deletes access; it does not erase uploaded objects, database history, or Firebase identity. Clear the encrypted cookie, queries/session, sockets, and local push state on success without another authenticated request. Device removal deactivates that notification registration and does not revoke a sign-in session.

AI usage ledger screens, CRUD services, demo fixtures, and portal proxy access are removed. Delivery tools require SuperAdmin and the backend allowlist. Production legal/FAQ text comes from the API; demo samples remain clearly illustrative and do not establish policy/retention commitments.

## Demo And Live Boundary

All modules use the same domain services and authenticated proxy in both modes. Demo validation, ownership, counts, visibility, and mutations are server-owned; reset must clear every module store. [Demo mode](DEMO_MODE.md) explains lifecycle and simulation. [Integrations](INTEGRATIONS.md) records retained live gaps; complete demo behavior and a successful build never prove configured live authorization, storage, delivery, serving, or persistence.
